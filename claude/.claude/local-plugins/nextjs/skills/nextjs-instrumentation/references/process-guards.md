# Process guards

Part of the `nextjs-instrumentation` skill: what Next already does with unhandled rejections and uncaught exceptions, and what a guard of the app's own adds.

- **Next already listens for `unhandledRejection` and `uncaughtException`:** it logs each one and keeps the process running, under `next start`, the standalone server and `next dev` (15.5 and 16.4). So Node's default (exit on an unhandled rejection) never happens in a Next server, and an uncaught exception doesn't end it either. In 16 an uncaught exception is printed twice in production (three times in development).
- **What a guard adds** is the decision to end the process: always on an uncaught exception (its state may be corrupt; the platform starts a clean one), and on unhandled rejections only past a budget within a sliding window (a slow leak shouldn't keep a degraded process alive for ever). Before exiting, run the shared flush (`shutdown.md`) and let stdout and stderr drain, with a time limit, or the line explaining the exit is lost.
- **Exiting only helps if something restarts the process:** a container platform does; on a VM it needs a supervisor (systemd's `Restart=`, pm2). Without one, the guard takes the site down. It also ends `next dev` on an uncaught exception. Check, and say so.
- **Next already prints each one,** so the guard doesn't log every rejection again: it logs its decision to exit and why. It logs with `console`, so it works when logging is what's broken; a console bridge carries it to telemetry.
- **Next 16 filters `unhandledRejection` listeners:** it patches `process.on`, `process.listeners` and `process.removeAllListeners` for that event, so `process.listenerCount('unhandledRejection')` reports 1 however many are registered, and `removeAllListeners` clears only its own list. A guard registered with `process.on` still fires; to check it's registered, use `process.listeners()`, not `listenerCount`.
- **`experimental.removeUncaughtErrorAndRejectionListeners`** makes Next remove the listeners for both events when its server is constructed, which is before `register()` runs (15.5 and 16.4), so guards registered in `register()` survive it.
